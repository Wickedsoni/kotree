# interview: kotlin

## kotlin/first-programs/where-a-program-starts
interview-questions:
- [intern] What is the entry point function of a standalone Kotlin application?
- [junior] How does the signature of the `main` function differ in Kotlin compared to older Java `public static void main(String[] args)`?
- [mid] Why does Kotlin allow top-level functions without enclosing classes, and how does the compiler represent them under the hood?
- [senior] What goes wrong in production when multiple files define conflicting top-level functions or properties with the same JVM signature?
what-interviewers-listen-for:
- Kotlin programs start execution from the `main(args: Array<String>)` function.
- Top-level functions are compiled into synthetic Java classes whose name is derived from the file name (e.g., `MainKt`).
- JVM name clashes can occur if `@JvmName` annotations are omitted when interoperating with Java codebases.
build-exercise: Create a Kotlin file with a top-level `main` function and a top-level helper function, compile it, and inspect the generated bytecode class name using IntelliJ/Android Studio bytecode viewer.
official-references:
- Basic syntax | https://kotlinlang.org/docs/basic-syntax.html
- Program entry point | https://kotlinlang.org/docs/basic-syntax.html#program-entry-point
common-wrong-beliefs:
- Every Kotlin function must be enclosed inside a class body | Kotlin supports top-level functions and properties directly inside packages without requiring a wrapping class.

## kotlin/types-and-variables/val-vs-var
interview-questions:
- [intern] What is the difference between `val` and `var` in Kotlin?
- [junior] Does `val` guarantee that the object referenced by the variable is immutable?
- [mid] Why does Kotlin strongly encourage immutability (`val`) over mutability (`var`) in everyday code?
- [senior] What goes wrong in production when developers assume a `val` property backed by a custom getter is constant or thread-safe?
what-interviewers-listen-for:
- `val` declares a read-only (reassign-once) reference; `var` declares a mutable variable.
- `val` does not guarantee deep object immutability if the referenced object exposes mutable state (e.g., `val list = mutableListOf()`).
- Custom getters evaluate every time the `val` is accessed, which can cause performance overhead or inconsistent values if state changes.
build-exercise: Declare a `val` holding a `MutableList`, add items to it after assignment, and observe that while the reference cannot be reassigned, the collection contents mutate successfully.
official-references:
- Basic types | https://kotlinlang.org/docs/basic-types.html
- Properties | https://kotlinlang.org/docs/properties.html
common-wrong-beliefs:
- A `val` variable is a true immutable constant equivalent to Java's `final` primitive or `const` | `val` is a read-only reference; if it wraps a mutable object, the underlying object can still change, and custom getters can return different values on every read.

- Kotlin basic types are always heavyweight wrapper objects like Java's `java.lang.Integer` | Kotlin compiles basic types to primitive JVM bytecodes (`int`, `long`, `double`) whenever possible for performance.
